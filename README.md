# ABTIK — Smart Campus & Provincial Mobility

Production blueprint for a hybrid **Grab-style motorcycle ride-hail** + **Life360 Safety Circles** app, built for university students and late-shift workers commuting on narrow, dark interior roads (*sudlunon*).

## Stack

| Layer | Choice |
| --- | --- |
| Mobile | React Native + Expo (TypeScript), Expo Router |
| Backend | Supabase (Auth, Postgres, Realtime, Edge Functions) |
| Spatial | PostGIS `geography(POINT, 4326)` + GiST indexes |
| Maps | `react-native-maps` + `expo-location` / TaskManager |
| Auth | Supabase Auth (session restore; demo mode needs none) |

## Quick start

> **Demo/presentation mode:** steps 1–6 are optional for a live demo —
> `npm install && npx expo start` boots straight into instant demo mode
> (role cards → dashboards, no backend) with a keyless dark map fallback.

1. Create a Supabase project and enable **PostGIS**.
2. Optional — enable **Phone auth** (Dashboard → Authentication → Providers →
   Phone) if you want real Supabase sessions; the shipped UI is demo-first
   and never asks for an SMS code. Add test numbers or a Twilio/EASMS provider.
3. Run migrations **in order** from `supabase/migrations/` (SQL editor or CLI):
   `20241027000000_init_abtik.sql` then `20261031000001_fix_ride_flow_rpcs_and_rls.sql`.
4. In Dashboard → Database → Replication, confirm `rides`, `trip_location_logs`, and `drivers` are on Realtime.
5. Copy `.env.example` → `.env` and set:
   - `EXPO_PUBLIC_SUPABASE_URL`
   - `EXPO_PUBLIC_SUPABASE_ANON_KEY`
6. Add Google Maps API keys in `app.json` (`ios.config.googleMapsApiKey`, `android.config.googleMaps.apiKey`).
7. Install & run:

```bash
npm install
npx expo start
```

Quality gates (both must be green):

```bash
npm run typecheck   # tsc --noEmit
npm run lint        # eslint .
```

To release trips to a driver, verify them once from the SQL editor:

```sql
UPDATE public.drivers SET vetted_status = TRUE WHERE id = '<driver-auth-uuid>';
```

Placeholder `assets/icon.png`, `splash-icon.png` and `adaptive-icon.png` are
generated by `npm run assets:placeholder` — replace them with the final artwork
before a store submission (same filenames, no config changes needed).

## Core product flows

### Sign-in

1. **Instant demo mode** — Get Started → Passenger or Driver role card →
   straight into that dashboard. No SMS/OTP/ID check; mock state lives in
   `src/lib/demoMode.ts` so every feature works immediately. Both dashboards
   offer **Switch Role** for seamless Passenger ⇄ Driver demos.
2. **Real sessions** — when a Supabase session already exists, Get Started
   skips role-select and lands on the matching dashboard. Drivers additionally
   need a `drivers` row (created in-app) and admin vetting before going online.

### Passenger

1. **Home** — dark campus map, hub pins, tap-to-set drop-off on interior roads.
2. **Booking** — distance + base fee + late-night provincial surcharge (**estimate only** —
   the authoritative fare is computed by `create_ride` with PostGIS `ST_Distance`).
3. **Active ride** — driver card, 4-digit OTP, Safety Circle live badge, SOS.

### Driver

1. **Setup** — plate, motorcycle, license → pending vetting.
2. **Dashboard** — online/offline toggle updates `drivers.current_location`.
3. **Incoming modal** — campus pickup vs drop-off complexity, fare, 20s accept timer.
4. **Trip** — OTP keypad → `start_ride` RPC (server-side verification) → background
   GPS on channel `ride_${rideId}_location` → turn-by-turn deep link.

## Realtime architecture

```
Driver device (expo-location background task)
        │  every ~3s
        ▼
createRideLocationPublisher(rideId)
        ├─ Broadcast event `location` on channel ride_{id}_location
        └─ INSERT trip_location_logs (durable / guardian replay)

Passenger & Guardians
        └─ subscribeToRideLocation(rideId) → map marker updates
```

Ride lifecycle still uses `postgres_changes` on `rides` for status (`requested` → `completed`).

## Database highlights

- Enums: `user_role`, `ride_status`
- Spatial: `drivers.current_location`, `rides.pickup/dropoff_location`
- `find_nearby_drivers(pickup, radius, limit)` — PostGIS KNN for matching (auth-only)
- `create_ride` — fare computed with `compute_fare` (ST_Distance + base + PHT
  night surcharge); no client-trusted amount is accepted anymore
- `accept_ride` — race-safe driver assignment (vetted + online + 5 km), rotates OTP
- `start_ride` — server-side OTP comparison, 5 attempts then 5-minute lockout
- `update_driver_location` — safe geography writes (auth-only)
- RLS: passengers own circles; ride peers + linked guardians can read live trips;
  **nearby online+vetted drivers can see `requested` rides within 5 km** (feed);
  driver rows are own-or-ride-peer only (no more world-readable GPS/license);
  guardian trip logs only while the ride is `accepted|arrived|in_progress`
- Auto OTP trigger on ride insert (pgcrypto-backed `generate_otp()`)
- `rides_guard` / `drivers_guard` triggers: fare, OTP, route and vetting are
  server/admin-owned; status follows a fixed state machine

## Implementation plan (ship sequence)

### Phase 0 — Foundations (this blueprint)

- [x] Schema, RLS, spatial indexes, Realtime publication
- [x] Typed Expo app shell (passenger + driver routes)
- [x] Supabase client + location broadcast helpers
- [x] Background location hook
- [x] Active ride + driver trip screens

### Phase 1 — Auth & profiles

- [x] Wire Supabase Auth (session persistence + profile context) — `AuthProvider`;
  phone-OTP UI retired in favour of instant demo mode (role cards).
- [x] Replace demo UUIDs with `auth.getUser()` (`useAuth().userId` everywhere).
- [x] Driver onboarding: plate, motorcycle, license in-app → `vetted_status` admin gate.

### Phase 2 — Matching & fare

1. On `create_ride`, Edge Function calls `find_nearby_drivers` and notifies online drivers (FCM / Expo Push).
2. Persist fare breakdown; LGU-configurable surcharge table (model lives in `compute_fare` today).
3. Idempotent accept (`accept_ride` RPC: `status = requested` + `driver_id IS NULL` guard).

### Phase 3 — Safety Circle productionization

1. Guardian invite via SMS deep link; verify phone ownership.
2. Deploy Edge Function `ride-sos`: notify guardians, campus security, optional call relay.
   (Client already falls back to native SMS/dial when it is down.)
3. Trip share link for non-app guardians (read-only web map).

### Phase 4 — Landmarking

1. Upload landmark photo to Supabase Storage (`landmark_image_url`).
2. Optional short audio note for unmapped drop-offs.
3. Driver complexity scoring from notes + night + distance from road network.

### Phase 5 — Hardening

1. Rate-limit OTP attempts ✅ (`start_ride` attempt counter + lockout); hash OTP
   at rest if compliance requires (pre-accept leaks are already closed by
   rotation in `accept_ride`).
2. Location sample downsampling + retention policy on `trip_location_logs`.
3. E2E: Detox/Maestro for book → accept → OTP → complete.
4. Observability: Sentry + Supabase logs on Edge Functions.
5. Dispatch feed could move to a dedicated table without `otp_code` / `passenger_id`.

## Security notes

- Never expose service role keys in the mobile app.
- Sessions persist in the device Keychain/Keystore (`src/lib/authStorage.ts`), not plain AsyncStorage.
- Guardians only see location while ride is `accepted|arrived|in_progress` (RLS).
- Background location must disclose purpose in store listings (Safety Circle).
- Treat SOS as a privileged action — confirm UI + server-side audit row.
  The client never reports success it did not earn: backend → guardian SMS →
  guardian call → 911 → explicit failure.
- Fare, OTP, route and vetting cannot be written by client statements
  (`rides_guard` / `drivers_guard` triggers); the only ride write path for
  clients is the guarded status state machine.
- `otp_code` is stripped from every driver-facing read (row selects and
  realtime payloads) and is rotated on acceptance; only the passenger can read it.

## Publishing (EAS Build)

```bash
npx eas-cli login                  # free account at expo.dev
npx eas-cli build -p android --profile preview   # installable APK
```

The `preview` profile (see `eas.json`) produces an APK you can install on any
Android phone — ideal for stage demos with no laptop tether. The placeholder
Google Maps key falls back to the built-in dark vector map, so **no Maps key
is required** for a demo build. Use the `production` profile for a Play Store
AAB.

> **Note:** EAS builds do not upload `.env` (it is gitignored), so
> `EXPO_PUBLIC_*` vars are undefined in cloud builds — the Supabase client
> falls back to demo placeholders and the app runs fully offline in demo
> mode. No backend is required for the presentation APK.
